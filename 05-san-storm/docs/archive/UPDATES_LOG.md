## 2026-02-08 - CSV字段命名完全统一（id → character_id）

### 更新内容

#### 1. 角色CSV字段最终统一

**修改原因**：
- 将 `id` 改为 `character_id`，与其他字段保持命名一致性
- 所有角色相关字段都使用 `character_` 前缀
- 与技能、羁绊的命名规范保持一致

**字段更新**：
```csv
旧格式：id,character_name,rarity,...
新格式：character_id,character_name,rarity,...
```

**命名统一性**：
```
角色CSV：character_id, character_name, character_type
技能CSV：skill_id, skill_name, character_type
羁绊CSV：bond_id, bond_name, ...
```

所有模板都遵循：`{类型}_id, {类型}_name` 的命名规范

#### 2. 工具脚本更新

**已更新的脚本**（2个）：
- ✅ `tools/hero-csv-to-json.cjs` - 更新字段引用
- ✅ `tools/hero-reset-and-regenerate.cjs` - 更新字段引用

**转换逻辑**：
```javascript
// CSV → JSON 转换
{
  id: row.character_id,  // character_id → id
  name: row.character_name,  // character_name → name
  characterType: row.character_type,  // character_type → characterType
}
```

#### 3. 文档更新

**已更新的文档**：
- ✅ `CHARACTER_SYSTEM.md` - 更新字段命名规范章节（6.1）
  - 添加character_id字段说明
  - 更新字段对照表
  - 更新自动转换规则

#### 4. 验证测试

**测试结果**：
```bash

node tools/hero-csv-to-json.cjs
✅ 成功转换180个角色
✅ id字段正确生成（从character_id转换）
```

### 命名规范总结

**CSV文件（snake_case）**：
```
角色：character_id, character_name, character_type, birth_year, death_year
技能：skill_id, skill_name, character_type
羁绊：bond_id, bond_name
```

**JSON文件（camelCase）**：
```
角色：id, name, characterType, birthYear, deathYear
技能：id, name, characterType
羁绊：id, name
```

**自动转换规则**：
- `character_id` → `id`
- `character_name` → `name`
- `character_type` → `characterType`
- `birth_year` → `birthYear`
- `death_year` → `deathYear`

### 设计理念

1. **命名一致性** - 所有CSV字段使用下划线命名
2. **前缀统一** - 角色相关字段都使用 `character_` 前缀
3. **自动转换** - 工具脚本自动处理命名转换
4. **向后兼容** - JSON字段名保持简洁（id, name）
5. **易于理解** - CSV字段名更明确（character_id vs id）

**修改原因**：
- 部队卡ID应该与角色ID规则保持一致
- 便于按赛季和势力管理部队卡
- 稀有度和兵种类型使用独立字段，不在ID中体现

**原格式**：
```
troop_{兵种代码}_{稀有度数字}{编号}
troop_i_5001  // 步兵，金色，第1个
troop_c_4001  // 骑兵，橙色，第1个
troop_a_3001  // 弓兵，紫色，第1个
```

**新格式**：
```
troop_{系列代码}_{赛季}{势力}{编号}
troop_san_1101  // S1赛季，刘备势力，第1个
troop_san_1301  // S1赛季，曹操势力，第1个
troop_san_1001  // S1赛季，通用部队，第1个
```

- `san` - 三国系列

- `3` - S3赛季（194年 群雄割据）

- `1` - 刘备势力
- `2` - 孙坚势力

- `4` - 汉室势力
- `5` - 董卓势力
- `6` - 袁绍势力

**编号**（2位）：

- 🎮 **玩家先动** - 组成阵型后玩家获得先手权
- 🤖 **自动攻击** - 阵型内部队自动选择最近敌人攻击
- ⚡ **一次性使用** - 阵型移动和攻击后自动解除

#### 2. 新增阵型规则

**阵型使用流程**：
```
1. 战斗开始 → 选择是否使用阵型
2. 选择阵型类型（锋矢/鹤翼/鱼鳞等）
3. 布置阵型位置
4. 玩家获得先手权
5. 阵型移动（移动距离=最低移动力）
6. 确认移动
7. 自动攻击（攻击最近敌人或进入防御状态）
8. 阵型自动解除
9. 进入正常回合制战斗
```

**移动规则**：
- 移动距离 = 阵型内所有部队的最低移动力
- 示例：部队移动力分别为2、3、5 → 阵型移动距离=2格
- 遇到障碍物：该部队在障碍物前停止，其余部队继续移动
- 阵型可能因障碍物而变形

**攻击规则**：
- 每支部队独立选择最近的敌对单位
- 使用曼哈顿距离计算（棋盘格距离）
- 无最近敌人则进入防御状态（防御+10%）
- 防御状态持续当前回合，显示盾牌图标🛡️

**阵型解除**：
- 阵型移动完成后自动解除
- 所有部队攻击完成后自动解除
- 解除后进入正常回合制战斗
- 每场战斗只能使用一次阵型

#### 4. 君主AI决策系统

**远交近攻原则**：

**联合申请决策**：
```
是否接壤？
├─ 否 → 偏向同意（80%）- 远交，无领土冲突
└─ 是 → 详细判断
    ├─ 对方强势（>1.5倍）→ 同意（70%）- 寻求保护
    ├─ 对方弱势（<0.7倍）→ 拒绝（70%）- 联合无益
    └─ 势力相当 → 综合判断
        └─ 有共同敌人 → 同意（80%）
```

**敌对申请决策**：
```
是否接壤？
├─ 否 → 偏向拒绝（80%）- 远交，无必要树敌
└─ 是 → 详细判断
    ├─ 对方弱势（<0.7倍）→ 同意（80%）- 可以扩张
    ├─ 对方强势（>1.5倍）→ 拒绝（80%）- 避免冲突
    └─ 势力相当 → 综合判断
        └─ 有领土争端 → 同意（70%）
```

#### 5. 七大势力AI谈判

**谈判流程**：
```
周四 01:00 - 收集决策结果
    ↓
周四 01:30 - 双向匹配
    - 联合必须双方都同意
    - 敌对只需一方同意
    ↓
周四 02:00 - 冲突解决
    - A想联合B，B想敌对A → 敌对优先
    - A想联合B和C，但B和C互相敌对 → 选择更有利的
    ↓
周四 02:30 - 平衡检查
    - 超级联盟（3+势力）→ 其他势力自动对抗
    - 势力被孤立 → 强制解除部分敌对
    ↓
周四 03:00 - 最终确定
    ↓
周四 08:00 - 全服公告
```

#### 6. 外交效果

**联合关系** 🤝：
- ❌ 不可互相攻击
- ✅ 共享地图视野

- ✅ 攻城速度+15%
- ✅ 击败敌对玩家声望+50%

**中立关系** ⚪：
- ✅ 可以攻击
- ✅ 无特殊效果

#### 7. 动态平衡机制

**自动平衡触发**：
- 某势力战力过强（>平均×2.0）→ 其他势力倾向联合对抗
- 某势力被孤立（所有势力敌对）→ 强制解除部分敌对

## 2026-02-05 - 政治和魅力属性势力竞争机制

### 更新内容

#### 1. 魅力属性 - 卡池质量决定

**核心机制**：
- 势力AI根据魅力值总数发布卡池
- 7个势力按魅力值排名
- 排名越高，卡池质量越好（稀有概率越高）

**魅力值计算**：
```javascript
势力魅力值 = Σ(所有玩家的所有角色魅力值) × 势力AI魅力加成

示例：
刘备势力：100玩家 × 3角色 × 7.5魅力 × 1.1加成 = 2475
曹操势力：120玩家 × 3角色 × 7.0魅力 × 1.0加成 = 2520
```

**卡池质量差异**：
| 排名 | 卡池名称 | 传说概率 | 史诗概率 | 稀有概率 | 普通概率 |
|------|---------|---------|---------|---------|---------|
| 第1名 | SSR卡池 | 5% | 20% | 35% | 40% |
| 第2名 | SR+卡池 | 4% | 18% | 35% | 43% |
| 第3名 | SR卡池 | 3% | 15% | 35% | 47% |
| 第4名 | R+卡池 | 2% | 12% | 35% | 51% |
| 第5名 | R卡池 | 1% | 10% | 35% | 54% |
| 第6名 | N+卡池 | 0.5% | 8% | 35% | 56.5% |
| 第7名 | N卡池 | 0.3% | 6% | 35% | 58.7% |

**差距**：第1名比第7名多16.7倍传说概率！

**势力AI魅力加成**：

#### 2. 政治属性 - 资源发放决定

**核心机制**：
- 势力AI每天08:00根据政治值总数发放资源
- 政治值越高，资源发放越多
- 势力AI自带政治加成/减成

**政治值计算**：
```javascript
势力政治值 = Σ(所有玩家的所有角色政治值) × 势力AI政治加成

平均政治 = 势力政治值 / 玩家数 / 3
政治加成 = 平均政治 / 10

示例：
刘备势力：平均政治7.0 → 政治加成70%
董卓势力：平均政治5.4 → 政治加成54%，再×0.9（AI惩罚）
```

**资源发放公式**：
```javascript
基础资源 = 城市数量 × 城市发展度 × 100
最终资源 = 基础资源 × (1 + 政治加成) × AI加成

示例：
刘备势力（10城市，80%发展度，政治7.0）
基础资源 = 10 × 0.8 × 100 = 800
最终资源 = 800 × 1.7 × 1.0 = 1360粮草/人/天

董卓势力（8城市，60%发展度，政治5.4）
基础资源 = 8 × 0.6 × 100 = 480
最终资源 = 480 × 1.54 × 0.9 = 665粮草/人/天

差距：刘备势力比董卓势力多104%资源！
```

- 刘备：+0%（标准）

- 曹操：+5%（治世之能臣）
- 袁绍：+0%（标准）

```javascript
function calculateMoraleChange(killCount, lossCount) {

  const moraleChange = battleResult / 10;
```

**战斗后更新**：
```javascript
function updateMorale(character, killCount, lossCount) {
  const change = calculateMoraleChange(killCount, lossCount);
  character.morale = Math.max(0, Math.min(100, character.morale + change));
  
  // 检查状态
  if (character.morale >= 80) {
    character.moraleStatus = 'high';
    character.attackBonus = 1.1; // +10%
  } else if (character.morale <= 20) {
    character.moraleStatus = 'low';
    character.attackBonus = 0.9; // -10%
  } else {
    character.moraleStatus = 'normal';
    character.attackBonus = 1.0;
  }
}
```

```javascript
function handleTroopDestroyed(character) {

}
```

```javascript
function restRecovery(character) {

  }
}
```

- 困难任务：难度值3
- 普通任务：难度值1
- 总难度上限：4

**任务组合示例**：
```
1个困难 + 1个普通 = 3 + 1 = 4（2个任务）
4个普通 = 1 + 1 + 1 + 1 = 4（4个任务）
1个困难 + 0个普通 = 3（1个任务，不推荐）

```

#### 2. 周常任务机制

**刷新时间**：
- 每周一 02:00 发布新周常

**提前结算机制**：
- 周常任务完成后，检查距离下周一的天数
- 如果剩余天数 > 2天，立即发布新周常
- 如果剩余天数 ≤ 2天，等待下周一

**提前结算示例**：

**随机流程**：
```
第1次随机 → 生成方案A1、B1、C1
第2次随机 → 生成方案A2、B2、C2

    ↓

    ↓
玩家选择1个方案
```

**防止重随机制**：
```javascript
// 保存9个方案到数据库
function saveSchemes(userId, schemes) {
  db.characterCreation.insert({
    userId: userId,
    schemes: schemes,
    createdAt: Date.now(),
    expiresAt: Date.now() + 7 * 24 * 60 * 60 * 1000, // 7天后过期
  });
}

// 检查是否已有方案
function checkExistingSchemes(userId) {
  const data = db.characterCreation.findOne({ userId: userId });
  
  if (data && data.expiresAt > Date.now()) {
    // 方案未过期，返回已有方案
    return data.schemes;
  } else {
    // 方案已过期或不存在，生成新方案
    const schemes = generateNineSchemes();
    saveSchemes(userId, schemes);
    return schemes;
  }
}
```
