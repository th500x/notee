# ID 命名规范

**版本**: v2.0  
**更新时间**: 2026-02-07

## 概述

为了保证游戏的可扩展性，所有游戏对象的ID统一使用**四位数编号**格式。

---

## 通用格式

```
{类型前缀}_{分类代码}_{四位数字}
```

### 示例
- `event_tk_0001` - 三国事件第1个
- `char_hero_0001` - 英雄武将第1个
- `city_youzhou_0001` - 幽州城市第1个
- `troop_i_1001` - 步兵白色第1个

---

## 事件 ID (Event)

### 格式
```
event_{分类}_{四位数字}
```

### 分类代码

| 代码 | 说明 | 示例 |
|------|------|------|
| `tk` | 三国历史事件 | `event_tk_0001` |
| `daily` | 日常事件 | `event_daily_0001` |
| `fiction` | 虚构事件 | `event_fiction_0001` |
| `season` | 赛季专属事件 | `event_season_0001` |
| `special` | 特殊事件 | `event_special_0001` |
| `tutorial` | 新手教程事件 | `event_tutorial_0001` |

### 编号范围

| 范围 | 用途 |
|------|------|
| 0001-0999 | 通用事件 |
| 1000-1999 | S1赛季专属 |
| 2000-2999 | S2赛季专属 |
| 3000-3999 | S3赛季专属 |
| 4000-4999 | 特殊活动事件 |
| 5000-9999 | 预留扩展 |

### 示例
```javascript
event_tk_0001      // 桃园结义
event_tk_0002      // 虎牢关之战
event_tk_0100      // 第100个三国事件
event_tk_1000      // S1专属：黄巾起义
event_daily_0001   // 日常事件：市集购物
event_fiction_0001 // 虚构事件：穿越时空
```

### 格式

- 第1位数字：赛季（1=S1, 2=S2, 3=S3...）
- 第2位数字：势力（1=刘备, 2=曹操, 3=孙坚...）

### ID优势

**通过ID即可了解角色信息**：
```javascript
char_san_1201
    ↓
char = 角色
san = 三国系列
1 = S1赛季
2 = 曹操势力
01 = 第1个角色（曹操本人）
```

**便于排序和管理**：
- 按赛季排序：1xxx < 2xxx < 3xxx
- 按势力排序：x1xx < x2xx < x3xx
- 按角色排序：xx01 < xx02 < xx03

**便于查询**：
```javascript
// 查询S1赛季所有角色
SELECT * FROM characters WHERE id LIKE 'char_san_1%'

// 查询刘备势力所有角色
SELECT * FROM characters WHERE id LIKE 'char_san_%1%'

// 查询曹操势力所有角色
SELECT * FROM characters WHERE id LIKE 'char_san_%2%'

// 查询孙坚势力所有角色
```

### 注意事项

⚠️ **重要**：
1. **不再使用稀有度前缀** - 稀有度信息在`rarity`字段中
2. **ID更简洁** - 从`char_legend_0001`改为`char_san_1101`
3. **信息更丰富** - 通过ID就能知道赛季、势力、编号
4. **便于排序** - 自动按赛季、势力、编号排序
5. **便于查询** - 可以快速筛选特定赛季或势力的角色

### 旧格式 vs 新格式

### ID优势

**通过ID即可了解部队卡信息**：
```javascript
troop_san_1201
    ↓
troop = 部队卡
san = 三国系列
1 = S1赛季
2 = 曹操势力
01 = 第1个部队卡（虎豹骑）
```

**与角色ID规则完全一致**：
```javascript
// 角色ID
char_san_1201   // 曹操（S1赛季，曹操势力，第1个角色）

// 部队卡ID
troop_san_1201  // 虎豹骑（S1赛季，曹操势力，第1个部队卡）
```

**便于排序和管理**：
- 按赛季排序：1xxx < 2xxx < 3xxx
- 按势力排序：x0xx < x1xx < x2xx < x3xx
- 按编号排序：xx01 < xx02 < xx03

**便于查询**：
```javascript
// 查询S1赛季所有部队卡
SELECT * FROM troops WHERE id LIKE 'troop_san_1%'

// 查询刘备势力所有部队卡
SELECT * FROM troops WHERE id LIKE 'troop_san_%1%'

// 查询曹操势力所有部队卡
SELECT * FROM troops WHERE id LIKE 'troop_san_%2%'

// 查询孙坚势力所有部队卡
SELECT * FROM troops WHERE id LIKE 'troop_san_%3%'

// 查询S1赛季曹操势力所有部队卡
SELECT * FROM troops WHERE id LIKE 'troop_san_12%'

// 查询通用部队卡（所有势力可用）
SELECT * FROM troops WHERE id LIKE 'troop_san_%0%'
```

### 重要说明

- ✅ **稀有度不在ID中体现**，使用独立的 `rarity` 字段
- ✅ **兵种类型不在ID中体现**，使用独立的 `troopType` 字段
- ✅ **ID规则与角色ID规则保持一致**
- ✅ **便于按赛季和势力管理部队卡**
- ✅ **通用部队（势力编号0）所有势力都可以使用**

```javascript
char_legend_0002     // 曹操
char_legend_0003     // 孙坚

// 预留扩展空间
event_tk_0001        // 第1个
event_tk_0100        // 第100个（中间还有99个空位）
```

### ❌ 避免的做法

```javascript
// ❌ 三位数编号（扩展性差）
event_tk_001
event_tk_999  // 只能到999

// ❌ 不规范的命名
event_1
event_taoyuan
char_liubei

// ❌ 没有分类
event_0001  // 不知道是什么类型的事件
```

## 总结

### 优势

1. **可扩展性强** - 每个类型最多支持9999个对象
2. **易于管理** - 清晰的分类和编号
3. **避免冲突** - 统一的命名规范
4. **便于查找** - 通过ID就能知道对象类型
5. **预留空间** - 充足的编号空间用于未来扩展

### 使用建议

1. 严格遵循四位数编号格式
2. 按类型和稀有度合理分配编号范围
3. 预留足够的编号空间
4. 在代码中使用常量定义ID
5. 定期整理和归档已使用的ID

---

**记住：所有ID都使用四位数编号！** 🎯
